# Order Queue Bot

Автоматизация: держит в "активной очереди" N заявок, следит за DOM,
довзятие через периодический reload. Управление — через Telegram
(`/start_session`, `/run`, `/stop`, `/status`), включая проброс 2FA-кода.

## Структура проекта

```
project/
├── Dockerfile
├── docker-compose.yml
├── requirements.txt
├── .env.example      # скопировать в .env и заполнить
├── tests/               # офлайн-тесты парсера и горячего цикла
├── tools/
│   ├── metrics_report.py # отчёт по замерам data/metrics.jsonl (см. ниже)
│   └── check_accounts.py # проверка кабинетов в .env перед запуском
└── app/
    ├── main.py            # точка входа (+ выбор бэкенда воркера)
    ├── config.py          # чтение env
    ├── state.py           # общее состояние между ботом и воркером
    ├── telegram_bot.py    # телеграм-команды
    ├── http_worker.py     # ГОРЯЧИЙ ЦИКЛ на httpx (без браузера) + замеры времени
    └── browser_worker.py  # Playwright: разовый логин/2FA + прежний цикл (fallback)
```

## Горячий цикл без браузера (httpx)

Опрос очереди и взятие заявок выполняются обычными HTTP-запросами через
`httpx` — без браузера, DOM и JS. Это снимает накладные расходы Playwright
(сетевой круг браузера, ожидание load, парсинг DOM), которые были основным
источником задержки в browser-версии.

Схема одного такта в режиме `take`:
1. `GET QUEUE_URL` по keep-alive соединению;
2. мгновенный разбор HTML регулярками → `payout_id`, `csrf_token`, `access_key`;
3. сразу `POST QUEUE_URL` с телом `csrf_token=…&act=take_payout&payout_id=…&access_key=` —
   ровно та же форма, что отправляет кнопка «Забрать выплату» в браузере;
4. подтверждение (что заявка появилась у нас) — фоновой задачей через `DEMANDS_URL`.

Ключевые оптимизации, уменьшающие **задержку обнаружения** заявки (именно она,
а не реакция клиента, ограничивает результат):
- **POST не блокирует цикл.** Как только заявку увидели, POST уходит отдельной
  задачей, а цикл сразу делает следующий `GET` — сетевой RTT отправки (~150–270 мс)
  перекрывается следующим опросом, а не удлиняет паузу между опросами.
- **Несколько воронок опроса** (`TAKE_PARALLEL_POLLERS`): очередь одновременно
  опрашивают N независимых циклов — окно обнаружения делится примерно на N.
  Дубликаты исключены общим набором `inflight` (проверка+пометка идут без `await`,
  значит атомарны для event loop).
- **Дедупликация.** Заявка, которую уже отправили (`inflight`), которая уже у нас
  (`taken_order_ids`) или которая уже «в работе» на площадке (`demands_ids` —
  включая автовыдачу и взятые до перезапуска процесса), не отправляется повторно.

### Сколько заявок держать: источник правды — страница demands

`TARGET_QUEUE_SIZE` — размер активной очереди. Считать его «по памяти» нельзя:
память бота (`taken_order_ids`) живёт только до перезапуска процесса, а часть
заявок площадка выдаёт **сама** (автовыдача — без нажатия «Забрать выплату»).
Поэтому перед стартом и далее раз в `DEMANDS_SYNC_S` секунд бот сверяется со
страницей `DEMANDS_URL` и считает слот занятым, если статус заявки —
«в работе у провайдера»:

- взятые нами (`taken_order_ids`) — знаем их и в памяти;
- выданные площадкой автоматически — в памяти их не было вовсе (бот пишет
  `📦 Автовыдача: #…` и учитывает их в занятых слотах);
- оставшиеся с прошлого запуска процесса — после рестарта память пуста, а слоты
  заняты, поэтому повторный `/run` не набирает лишние заявки;
- завершённые (статус уже не «в работе…») — слот освобождается: бот пишет
  `ℹ️ Заявка #… — убираю из очереди, слот свободен` и добирает заявки до цели.

Занятые слоты = объединение заявок «в работе» со страницы demands, взятых в этой
сессии и отправленных, но ещё не подтверждённых (`inflight`).

Если локальный кэш разошёлся с реальностью (например, после перезапусков «в работе
10», а по факту 1), команда `/reset_session` очищает память бота
(`taken_order_ids`/`demands_ids`/счётчик) и пересчитывает активную очередь строго
по странице demands: пока свежая сверка не прошла, воркер не берёт новые заявки.
Сессию сайта (cookies/auth.json) команда НЕ трогает — это не разлогин.

Если `DEMANDS_URL` недоступен, бот предупреждает и считает очередь по памяти
(после перезапуска возможен перебор); если слетела сессия — останавливается и
просит запустить кабинет заново (`/run`).

Браузер используется **только** для разовой авторизации (получение/обновление
куки в `auth.json`), когда сохранённая сессия перестала действовать. В самом
горячем цикле браузер не участвует.

### Замеры времени

На каждом взятии пишется JSONL-строка в `./data/metrics.jsonl` (путь
настраивается через `METRICS_PATH`) и в лог (`METRIC …`):

| поле | смысл |
|---|---|
| `saw_to_sent_ms` | **от «заявку увидели» (пришёл ответ GET) до «POST отправлен»** |
| `poll_rtt_ms` | сетевой round-trip самого GET очереди |
| `since_prev_get_ms` | окно между двумя опросами очереди (задержка обнаружения) |
| `parse_ms` | разбор HTML регулярками |
| `py_overhead_ms` | накладные расходы Python-клиента (без сети и парсинга) |
| `submit_rtt_ms` | сетевой round-trip POST |
| `http_status` | код ответа на POST |
| `take_result` → `confirmed` | отдельная запись: взяли заявку (`true`) или упустили (`false`) |
| `take_result` → `confirm_ms` | сколько заняло подтверждение через `DEMANDS_URL` |

Сопоставление `saw_to_sent_ms` с `poll_rtt_ms`/`submit_rtt_ms` (сеть),
`since_prev_get_ms` (частота опроса) и `py_overhead_ms` (Python) показывает, где
реально теряется время. Пример из реального прогона:

```
{"event":"take","order_id":"6416820","poll_rtt_ms":136.26,"parse_ms":0.6,
 "saw_to_sent_ms":0.61,"py_overhead_ms":0.01,"submit_rtt_ms":140.98,"http_status":200}
```

Здесь реакция клиента — **0.6 мс**, а вся задержка в сети и частоте опроса: значит
выносить код в Go бессмысленно, а сокращать потери нужно опросом (см. ниже).

### Отчёт по замерам

Сводку по всем замерам (перцентили, разбивка по кабинетам, доля взятых заявок)
строит скрипт:

```bash
python tools/metrics_report.py              # читает data/metrics.jsonl
python tools/metrics_report.py другой.jsonl # или явный путь
```

Показательный результат реального прогона (356 взятий, сутки работы, один воркер):

```
saw_to_sent_ms     p50=  0.59  p90=  1.00  p99=  6.68  макс=  9.46
py_overhead_ms     p50=  0.19  p90=  0.35  p99=  1.75  макс=  6.23
parse_ms           p50=  0.39  p90=  0.66
poll_rtt_ms        p50=141.90  p90=314.09  макс=2794.98
since_prev_get_ms  p50=529.66  p90=803.06  макс=9232.97
submit_rtt_ms      p50=155.67  p90=336.33  макс=4322.97
подтверждено: 50 / 348 (14.4%)
```

**Вывод по Go:** собственная логика Python (парсинг + запуск POST) — **0.59 мс
в медиане и меньше 10 мс в худшем случае за сутки**, то есть доли процента от
150+ мс сетевого round-trip. Переписывание горячего цикла на Go дало бы выигрыш
в пределах шума измерений, поэтому не оправдано. Настоящие рычаги — задержка
обнаружения (`since_prev_get_ms` ≈ 530 мс в медиане) и сеть:

- уменьшить `TAKE_POLL_MIN_MS`/`TAKE_POLL_MAX_MS` — окно опроса падает линейно;
- поднять `TAKE_PARALLEL_POLLERS` (>1) — N воронок делят окно обнаружения на N;
- низкая доля подтверждений (14.4%) при `http_status=200` — сигнал, что заявку
  забирает кто-то быстрее (или сайт отдаёт закешированную страницу очереди);
  смотреть на это надо вместе с `submit_rtt_ms`, а не с Python-частью.

### Переключение бэкенда

`WORKER_BACKEND` в `.env`:
- `http` (по умолчанию) — горячий цикл на httpx;
- `browser` — прежний Playwright-воркер (безопасный откат одной переменной).

## Перед первым запуском — обязательно

Откройте `app/browser_worker.py`, там в начале файла блок с селекторами
(`SEL_LOGIN_INPUT`, `SEL_ACTIVE_QUEUE_CARD`, `SEL_TAKE_BUTTON` и т.д.) —
заполните под реальную разметку вашего личного кабинета через DevTools
(правой кнопкой на элемент → Inspect → Copy selector).

## Локальная сборка и тест (опционально, до Hostinger)

```bash
cp .env.example .env
# заполните .env своими значениями

docker compose build
docker compose up
```

Логи будут в консоли и в `./data/actions.log`. Файл сессии сохранится
в `./data/auth.json` — при повторном запуске логин/2FA не потребуется,
пока сессия не протухнет.

## Деплой на Hostinger

### Нужен ли домен?

**Нет, не нужен.** Причины:
- Telegram-бот работает в режиме **long polling** — сам стучится к
  Telegram API наружу, входящих подключений извне на ваш сервер не
  требуется, значит и домен/SSL сертификат не нужны.
- Playwright просто открывает браузер внутри контейнера и ходит на
  внешний сайт заявок — тоже не требует, чтобы у вашего сервера был
  домен.

Домен нужен был бы только если бы вы хотели: (а) поставить Telegram-бота
в режим webhook вместо polling, или (б) сделать веб-интерфейс/дашборд,
доступный снаружи по имени. Для описанной задачи — не нужно. Можно
обойтись голым IP-адресом VPS.

### Шаги

1. **Выберите план на Hostinger** — нужен VPS (не shared-хостинг),
   т.к. нужен Docker и постоянно работающий процесс с браузером.
   Минимум 2 GB RAM — Chromium в контейнере довольно прожорлив,
   с 1 GB велик шанс OOM-килов.

2. **Установите Docker на VPS**, если панель Hostinger не предлагает
   его сразу (некоторые VPS-планы Hostinger идут с Docker из коробки
   через их шаблоны ОС):
   ```bash
   curl -fsSL https://get.docker.com | sh
   sudo systemctl enable docker
   ```
   Проверьте, что `docker compose` доступен (`docker compose version`);
   если нет — поставьте плагин `docker-compose-plugin`.

3. **Залейте проект на сервер.** Проще всего через git:
   ```bash
   # на сервере
   git clone <ваш-репозиторий> order-bot
   cd order-bot
   ```
   Либо через `scp`:
   ```bash
   # с вашего компьютера
   scp -r ./project root@ВАШ_IP:/root/order-bot
   ```

4. **Заполните `.env` на сервере** (не коммитьте его в git!):
   ```bash
   cp .env.example .env
   nano .env
   ```

5. **Соберите и запустите:**
   ```bash
   docker compose build
   docker compose up -d
   ```

6. **Проверьте логи:**
   ```bash
   docker compose logs -f
   ```

7. **В Telegram** напишите боту `/start_session` — он начнёт логин,
   попросит 2FA код, вы отправляете его обычным сообщением в чат,
   бот подтверждает вход и сохраняет сессию в `./data/auth.json`
   (примонтирован с хоста — переживёт пересборку контейнера).

8. Дальше управляете через `/run` и `/stop`.

### Автозапуск после перезагрузки сервера

`docker-compose.yml` уже содержит `restart: unless-stopped` — контейнер
поднимется сам после ребута VPS. Цикл мониторинга при этом не
запустится автоматически (`state.running=False` по умолчанию) — это
осознанно, чтобы после любого рестарта вы явным образом подтверждали
запуск командой `/run` из Telegram.

### Обновление селекторов/кода после первого деплоя

```bash
git pull   # или заново scp
docker compose build
docker compose up -d
```
Файл сессии в `./data/` не пересоздаётся при пересборке, повторный
логин не понадобится.

## Мультиаккаунт: несколько кабинетов одновременно

Бот может работать сразу с несколькими кабинетами (аккаунтами). На каждый
кабинет поднимается отдельная задача-воркер со своими cookies, своим опросом
очереди и своими заявками; в уведомлениях имя кабинета стоит в начале строки
(`[Кабинет 2] …`).

Настройка в `.env` — кабинет №1 как раньше, остальные с суффиксом-номером:

```bash
SITE_LOGIN=first@example.com
SITE_PASSWORD=...

SITE_LOGIN_2=second@example.com
SITE_PASSWORD_2=...
SITE_NAME_2=Кабинет 2          # необязательно: имя в уведомлениях
```

Кабинеты перебираются подряд, пока заданы `SITE_LOGIN_N`/`SITE_PASSWORD_N`
(если задан только один из пары — бот упадёт с понятной ошибкой).
Файлы сессий: `./data/auth.json`, `./data/auth_2.json`, `./data/auth_3.json`, …

Команды в Telegram:

| команда | что делает |
|---|---|
| `/run` (без аргументов) | спрашивает кабинеты: ответьте `1 3`, `1,3`, `1;3` или `all` |
| `/run 1 3`, `/run all` | запуск на взятие заявок для указанных/всех кабинетов |
| `/runall`, `/watchall`, `/stopall` | то же для всех кабинетов одной командой |
| `/stop` (без аргументов) | спрашивает, какие кабинеты остановить |
| `/status` | сколько кабинетов работает сейчас + состояние каждого |
| `/reset_session` | очистить кэш очереди кабинета и пересчитать по площадке (если «в работе» разошлось с реальностью); сессию сайта не трогает |

Особенности:
- Авторизация (когда сессия кабинета протухла) и ввод 2FA идут **по одной за
  раз**, чтобы не путать, чей код вводится; сами горячие циклы полностью
  параллельны. Если 2FA ждут сразу несколько кабинетов, присылайте код вместе
  с номером кабинета: `2 123456`.
- Мультиаккаунт работает на `WORKER_BACKEND=http` (по умолчанию).
  `WORKER_BACKEND=browser` при 2+ кабинетах запускает только кабинет №1 и
  пишет предупреждение в лог.
- Каждый кабинет опрашивает очередь независимо: `TAKE_PARALLEL_POLLERS` — это
  число воронок опроса **на один кабинет** (итого нагрузка ×N кабинетов).

### Проверка конфигурации кабинетов

Перед запуском убедиться, что кабинеты прочитались и сессии на месте (секреты
не печатаются — логин маскируется):

```bash
python tools/check_accounts.py              # читает .env
python tools/check_accounts.py path/to/.env # или явный файл
```

Скрипт показывает список кабинетов, пути их файлов сессий, число админов,
выбранный бэкенд и предупреждает, если `WORKER_BACKEND=browser` не сможет
запустить больше одного кабинета.

Важно: `load_dotenv()` **не перезаписывает** уже существующие переменные
окружения. Если вы когда-то делали `export SITE_LOGIN_2=…` (или `set -a;
source .env`) в этом же терминале, бот возьмёт старые значения из окружения, а
не из `.env` — запускайте его в чистом терминале либо снимите их (`unset`).
`check_accounts.py` такие «залипшие» переменные показывает.

## Безопасность

- `.env` с логином/паролем никогда не коммитьте в публичный репозиторий
  — добавьте `.env` в `.gitignore`.
- Кто может управлять ботом, задаётся списком id в `TELEGRAM_ALLOWED_CHAT_ID`
  (несколько — через запятую/пробел); можно также использовать
  `TELEGRAM_ADMIN_IDS` / `TELEGRAM_SUB_USERS` / `SUB_USER`. Не теряйте контроль
  над этими значениями — любой из админов может слать боту команды и 2FA-коды.
- Всем админам приходят уведомления (в т.ч. дампы HTML). Команда `/id` доступна
  любому и показывает его chat_id — удобно, чтобы добавить нового человека.
- Файл `./data/auth.json` — это фактически ваша живая сессия на сайте,
  относитесь к нему как к паролю.
